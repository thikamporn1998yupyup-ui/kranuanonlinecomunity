# กระนวนใกล้บ้าน — ระบบร้านและออเดอร์ส่วนกลาง

ชุดนี้ต่อจาก UI เวอร์ชันล่าสุดของเรา ใช้ Node.js 24.22.1 และ SQLite ในเซิร์ฟเวอร์เดียว ไม่มีแพ็กเกจ npm ภายนอก การเปลี่ยนฐานข้อมูลทำผ่าน API ที่ตรวจบัญชีและสิทธิ์บนเซิร์ฟเวอร์

## สิ่งที่ทำแล้ว

- สารบัญร้านอาหาร เครื่องดื่ม บริการ และร้านค้า พร้อมแหล่งข้อมูลและพิกัด
- เพิ่มร้านเอง นำเข้า JSON/Overpass JSON และปุ่มดึงร้านในเขตอำเภอกระนวนจาก OpenStreetMap
- สถานะเริ่มต้นของร้านที่เพิ่ม/นำเข้าคือยังไม่ตรวจสอบและปิดรับออเดอร์เสมอ
- บันทึกการลงพื้นที่ ผู้ยืนยัน และวันเวลายืนยัน แยกจากการตกลงเข้าร่วมและการเปิดขาย
- เมนู ราคา รูปสินค้า และปิดเมนูที่หมด เปิดร้านได้เมื่อยืนยัน + เข้าร่วม + มีเมนูพร้อมขาย
- ลูกค้าเลือกจำนวน ระบุชื่อ โทรศัพท์ ที่อยู่ หมายเหตุ และแนบ GPS โดยขอสิทธิ์จากเบราว์เซอร์
- เซิร์ฟเวอร์คิดราคาจากเมนูจริง กันกดส่งซ้ำ และเก็บประวัติสถานะ
- โหมดรับฝากซื้อส่งงานเข้าไรเดอร์ทันที หรือโหมดร้านยืนยันก่อนเปิดงานให้ไรเดอร์
- บัญชีผู้ดูแล ร้านค้า และไรเดอร์ สร้างโดยผู้ดูแล รหัสผ่านเก็บเป็น salted scrypt hash เซสชันใช้ HttpOnly cookie และตรวจ CSRF
- ไรเดอร์เปิดออนไลน์ รับงานคนเดียวต่อออเดอร์ และมีงานกำลังส่งได้ครั้งละหนึ่งงาน
- หน้าลูกค้า ไรเดอร์ และผู้ดูแลอัปเดตผ่าน SSE พร้อมโหลดสำรองทุก 15 วินาที
- ระบบแจ้งเตือนกลางจอ ภาพร้าน/สินค้า และกำลังใจอีสานเดิมยังอยู่
- ลูกค้าส่งพัสดุผ่าน API เดียวกันได้ บันทึกที่อยู่ปลายทางจริง
- ผู้ดูแลเปลี่ยนรหัสบัญชีทีมงานและยกเลิกเซสชันทุกเครื่องได้

## ก่อนนำขึ้น Render

ชุดนี้เป็น Web Service มีเซิร์ฟเวอร์และฐานข้อมูล จึงใช้แทน Static Site ด้วยการวาง HTML ไฟล์เดียวไม่ได้

โครงสร้างที่จะใส่ที่ root ของ repository:

    package.json
    server.cjs
    schema.sql
    render.yaml
    .node-version
    .gitignore
    public/
      index.html
      admin.html
      api.js
      customer.js
      admin.js
      rider-bridge.js
      system.css
      assets/
      rider/index.html
    scripts/
    tests/

นำเนื้อหาภายในโฟลเดอร์ kranuan-system ไปไว้ที่ root ของ GitHub repo ไม่ใช่นำเฉพาะ public/index.html ไปทับ index.html เดิม ไฟล์เก่าที่ root จะไม่ถูก server นี้เสิร์ฟ เว็บจะใช้ public/ เท่านั้น ส่วน assets ที่อ้างถึงรวมจาก GitHub ของคุณ ณ commit 9937a816a71d49dd79191c2184a9a31e7f3c8d49 มาแล้ว

ยังไม่ได้ push GitHub หรือแก้ Render จริงในรอบนี้ จึงยังไม่กระทบเว็บออนไลน์เดิม

## ตั้งค่า Render แบบทีละขั้น

1. อัปโหลดชุดไฟล์เข้า GitHub แล้วสร้าง Node Web Service ที่เชื่อม repo นี้ หากบริการเดิมเป็น Static Site ให้สร้าง Web Service แยกเพื่อทดสอบก่อน
2. Build command: node --check server.cjs
3. Start command: node server.cjs
4. Health check path: /api/health
5. Node version: 24.22.1
6. ใช้หนึ่ง instance และเพิ่ม Persistent Disk ขนาด 1 GB ที่ mount path /var/data
7. ตั้ง environment variables ตามตารางด้านล่างแล้ว deploy

| ตัวแปร | ค่า |
|---|---|
| NODE_ENV | production |
| NODE_VERSION | 24.22.1 |
| DATA_DIR | /var/data/kranuan |
| APP_ORIGIN | URL จริงของ Web Service เช่น https://ชื่อบริการ.onrender.com ไม่มี / ท้าย URL |
| ADMIN_USERNAME | admin หรือชื่อที่คุณกำหนด |
| ADMIN_PASSWORD | รหัสผ่านที่ตั้งเองอย่างน้อย 12 ตัวอักษร เก็บใน Render Environment เท่านั้น |
| DELIVERY_FEE_THB | 25 หรือค่าบริการคงที่ที่ตกลงใช้ |

ห้ามใส่ ADMIN_PASSWORD ลง GitHub หรือ public/*.js ไม่มีรหัสเริ่มต้นร่วมกันในชุดไฟล์นี้ บัญชีผู้ดูแลถูกสร้างจาก environment ตอนเริ่มระบบครั้งแรกเท่านั้น หลังสร้างแล้วเปลี่ยนรหัสที่หน้าบัญชีทีมงาน การเปลี่ยน environment อย่างเดียวไม่เปลี่ยนรหัสที่เก็บในฐานข้อมูลแล้ว

มี render.yaml สำหรับสร้างบริการชื่อ kranuan-community-system แยกจากเว็บเก่า โดยระบุแพ็กเกจแบบเสียเงิน 0.5c-512mb และ Persistent Disk ไว้ชัดเจน ระบบไม่ได้สร้างหรือจ่ายเงินให้โดยอัตโนมัติ ตรวจค่าใช้จ่ายใน Render ก่อนกดสร้าง หากใช้ Blueprint ให้กรอก APP_ORIGIN ให้ตรงกับ URL ที่ได้รับจริงแล้ว redeploy เมื่อจำเป็น

Render Free ไม่มี Persistent Disk และไฟล์ฐานข้อมูลอาจหายหลัง restart/redeploy ชุดนี้จึงกำหนดใช้ disk สำหรับข้อมูลจริง อ้างอิง: https://render.com/docs/disks และ https://render.com/docs/free

หาก URL เปลี่ยนหลังสร้าง Web Service ให้ใช้ URL ใหม่ทดสอบก่อน การเปลี่ยน LIFF endpoint / LINE OA ต้องทำแยกภายหลัง ชุดนี้ไม่ได้เปลี่ยนการตั้งค่าบัญชี LINE ของคุณ

## เริ่มใช้งาน

- ลูกค้า: /
- ผู้ดูแลและร้านค้า: /admin.html
- ไรเดอร์: /rider/

ลำดับเปิดร้าน:

1. ผู้ดูแลเข้าสู่ /admin.html ด้วยบัญชีที่ตั้งใน Render
2. เพิ่มร้านเองหรือนำเข้าข้อมูล ทุกร้านจะยังสั่งไม่ได้
3. ลงพื้นที่จริง แล้วกด “บันทึกการยืนยันร้าน” พร้อมบันทึกผู้ติดต่อ/หลักฐานการตรวจสอบ
4. แก้ไขข้อมูลร้านและเลือก “ร้านตกลงเข้าร่วมรับออเดอร์กับระบบแล้ว” เมื่อตกลงกับร้านแล้วจริง
5. เพิ่มเมนู ราคา และสถานะพร้อมขาย
6. เลือกรูปแบบ “ไรเดอร์รับฝากซื้อ” หรือ “ร้านยืนยันก่อนส่งงาน” ถ้าใช้แบบร้านยืนยัน ให้สร้างบัญชีร้านผูกกับร้านนั้นก่อน
7. กด “เปิดรับออเดอร์”
8. สร้างบัญชีไรเดอร์ให้คนที่ผ่านการรับเข้าระบบ ไรเดอร์เข้าหน้า /rider/ แล้วเปิดออนไลน์
9. ลูกค้าสั่งจาก / งานแบบรับฝากซื้อจะเด้งทันที ส่วนแบบร้านยืนยันจะยังไม่ให้ไรเดอร์รับจนกว่าร้านยืนยัน

การยืนยันร้านไม่ใช่การรับรองจากหน่วยงานรัฐ และไม่ได้เปิดร้านให้ขายโดยอัตโนมัติ ปิดรับออเดอร์หรือถอนยืนยันได้ตลอด การปิดร้านไม่ยกเลิกออเดอร์ที่มีอยู่แล้ว ผู้ดูแลจัดการเป็นรายงานได้

## นำเข้าข้อมูลร้านจริง

หน้า “นำเข้าร้าน” มีปุ่มค้นหา OpenStreetMap ด้วยขอบเขตอำเภอกระนวน ไม่ใช่กำหนดกรอบสี่เหลี่ยมแล้วเหมารวมร้านอำเภอข้างเคียง ร้านที่ไม่มีชื่อจะข้าม และ source_id เดิมจะไม่ถูกนำเข้าซ้ำหรือเขียนทับร้านที่ทีมงานตรวจแล้ว

ขณะพัฒนาทดลองเรียก Overpass แล้วพบ HTTP 406 และ timeout จึงยังไม่ได้ใส่รายชื่อร้านจริงในฐานข้อมูลเริ่มต้น และไม่มีการสร้างร้านสมมติทดแทนให้ดูเหมือนข้อมูลจริง ให้ลองนำเข้าจากหน้าผู้ดูแลหลังติดตั้ง หรือใช้ไฟล์ JSON จากการสำรวจ ตัวนำเข้ามีข้อความแจ้งข้อผิดพลาดเมื่อบริการต้นทางใช้ไม่ได้

ใช้ shops-import-template.json เป็นจุดเริ่มต้น โครงสร้างแต่ละรายการ:

    {
      "shops": [
        {
          "name": "กรอกชื่อจากร้านที่สำรวจจริง",
          "category": "อาหาร",
          "address": "กรอกที่ตั้งจริง",
          "phone": "เบอร์ติดต่อร้าน",
          "lat": null,
          "lng": null,
          "source": "survey",
          "source_id": "รหัสสำรวจของทีมงาน",
          "source_url": ""
        }
      ]
    }

ตัวอย่างด้านบนเป็นคำอธิบายรูปแบบ ไม่ใช่รายชื่อร้านจริง รองรับหมวด อาหาร / เครื่องดื่ม / บริการ / ร้านค้า ฟิลด์ verification, accepting หรือ opt_in ในไฟล์นำเข้าจะไม่ทำให้ร้านได้สถานะยืนยันหรือเปิดขาย

ข้อมูล OpenStreetMap ต้องแสดงเครดิตและปฏิบัติตาม ODbL รวมถึงเงื่อนไขเมื่อเผยแพร่ฐานข้อมูลที่ดัดแปลง ระบบเก็บ source_id/source_url และแสดงเครดิตในหน้ารายการร้าน แหล่งอ้างอิง: https://www.openstreetmap.org/copyright

ไม่ได้นำรูป รีวิว หรือรายชื่อจาก Google Maps มาเก็บเป็นฐานข้อมูล

## ขอบเขตของรุ่นนี้

- ค่าส่งคงที่ตาม DELIVERY_FEE_THB และแสดงก่อนยืนยัน ยังไม่ได้ใช้สูตรระยะทางใน assets/delivery-pricing.js เป็นราคาจัดส่งจริง
- ไม่มีตัดเงินออนไลน์ ลูกค้าเห็นยอดสินค้าและค่าส่งชัดเจน โหมดฝากซื้อไม่รวมค่าบริการอื่นนอกเหนือจากที่แสดง
- ลูกค้าใช้เซสชันประจำเบราว์เซอร์ ออเดอร์ของฉันไม่ซิงค์ข้ามมือถือ หากล้าง cookie จะไม่เห็นออเดอร์เก่า ต้องให้ผู้ดูแลค้นหา ยังไม่ได้ผูกบัญชีลูกค้ากับ LINE token ฝั่งเซิร์ฟเวอร์ รูป/ชื่อ LINE เดิมใช้แสดงผลเท่านั้น ไม่ใช้กำหนดสิทธิ์
- ต้องเปิดหน้าไรเดอร์ออนไลน์เพื่อรับการแจ้งเตือน SSE ยังไม่มี Web Push เมื่อปิดเว็บ, LINE Messaging API หรือ native push
- ตลาดลงประกาศยังเป็นส่วนทดลอง localStorage และมีข้อความกำกับ ไม่ใช่ตลาดประกาศส่วนกลาง การส่งพัสดุใช้ฐานข้อมูลกลางได้
- ยังไม่มีแผนที่ให้ปักหมุดเอง การสั่งอาหารแนบ GPS ได้และระบุที่อยู่จริงเสมอ ฟอร์มพัสดุใช้ที่อยู่ที่ลูกค้ากรอก
- ไม่มีเมนูตัวเลือกย่อย/สต๊อกนับชิ้น ใช้จำนวนและหมายเหตุ ราคาและรายการถูกเก็บเป็น snapshot เมื่อสั่ง
- การร้องเรียน/SOS ถูกบันทึกและแสดงในหน้าผู้ดูแล ยังไม่แจ้งหน่วยฉุกเฉินหรือโทรแทนผู้ใช้
- SQLite และ SSE ชุดนี้ออกแบบให้รันหนึ่งเซิร์ฟเวอร์ หากขยายหลาย instance ให้ย้ายฐานข้อมูลและการกระจาย event ก่อน

## ทดสอบในเครื่อง

ต้องมี Node.js 24.15 ขึ้นไปในสาย 24 แนะนำ 24.22.1 ไม่ต้อง npm install เพราะไม่มี dependency ภายนอก

PowerShell:

    $env:ADMIN_USERNAME='admin'
    $env:ADMIN_PASSWORD='ตั้งรหัสผ่านของคุณอย่างน้อย12ตัว'
    $env:NODE_ENV='development'
    node server.cjs

เปิด http://localhost:3000 และใช้หน้าต่างส่วนตัว/คนละเบราว์เซอร์แยกลูกค้า ไรเดอร์ และผู้ดูแล ไม่ใช่แท็บในโปรไฟล์เดียวกัน เพราะ cookie บัญชีจะใช้ร่วมกัน

รันชุดตรวจอัตโนมัติ:

    npm test

ผลตรวจ: ผ่าน 14 tests รวมการนำเข้า ร้านยังไม่ยืนยันสั่งไม่ได้ ราคาจากเซิร์ฟเวอร์ กดซ้ำไม่เพิ่มออเดอร์ สิทธิ์ผู้ใช้/CSRF สองไรเดอร์แย่งงานได้ผู้ชนะคนเดียว ขั้นตอนร้านยืนยัน การยกเลิก ประวัติสถานะ พัสดุ SSE และเปลี่ยนรหัสแล้วเพิกถอนเซสชัน

ตรวจผ่าน Chromium แยก browser context จริงอีกชุด: ผู้ดูแลยืนยัน+เข้าร่วม+เพิ่มเมนู+เปิดร้าน → ลูกค้าสั่ง → กล่องงานเด้งในหน้าไรเดอร์ → รับงาน/รับของ/ส่งสำเร็จ → ลูกค้าและผู้ดูแลเห็นสถานะอัปเดต ไม่มี JavaScript page errors ใช้ข้อมูลทดสอบในฐานข้อมูลชั่วคราวที่ลบหลังทดสอบ ไม่ปนข้อมูลผู้ใช้จริง

ยังไม่ได้ทดสอบ deployment ในบัญชี Render ของคุณ, การ login LINE จริง หรือดึงรายชื่อ OpenStreetMap สำเร็จ

## ฐานข้อมูลและสำรอง

ฐานข้อมูลอยู่ DATA_DIR/kranuan.sqlite ใช้ schema.sql สร้างตารางครั้งแรกโดยอัตโนมัติ เก็บผู้ใช้ เซสชัน ร้าน เมนู ออเดอร์ ประวัติสถานะ เรื่องแจ้ง และ audit

สำรองขณะระบบทำงานด้วย SQLite backup API:

    node scripts/backup.cjs /var/data/kranuan-backup.sqlite

เก็บ backup ไว้นอก public/ และสำรองออกนอกบริการตามรอบที่คุณต้องการ ห้าม commit ฐานข้อมูล ออเดอร์ รหัสผ่าน หรือ backup เข้า GitHub

เมื่อ restore ให้หยุดเซิร์ฟเวอร์ก่อน เปลี่ยนไฟล์ฐานข้อมูลจาก backup และจัดการไฟล์ WAL/SHM ของฐานข้อมูลเดิมให้ถูกต้อง อย่านำไฟล์ backup ไปเปิดเป็นไฟล์ public
